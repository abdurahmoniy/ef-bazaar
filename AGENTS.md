# Project rules

These rules apply to the entire efBazaar monorepo. Read `CLAUDE.md` for domain and architecture conventions. The current workflows, package manifests, and service configuration are the source of truth for build commands and runtime versions.

## Test first

- Before changing behavior, identify the expected result and the affected services, clients, and event consumers.
- For features and bug fixes, add or update a meaningful regression test first. Run it and confirm it fails for the expected reason before changing production code. An existing failing test is sufficient when it reproduces the reported bug.
- Implement the smallest complete fix, then run the focused tests. Test observable behavior and permissions, including relevant failure paths; do not merely mirror the implementation.
- For documentation-only changes, verify accuracy, links, and the diff. Do not add artificial tests or run unrelated application suites.

## Verify the whole affected scope

Focused tests are a development aid, not the completion gate. Before declaring implementation finished or pushing code, run the full checks for every affected component on the final code.

Read `.github/workflows/ci.yml`, and relevant build/deploy workflows, before choosing checks. Include dependencies affected by shared API, schema, event, authentication, or infrastructure changes, even when path filters would skip them.

Reinstall dependencies when the lockfile or environment changes. If workflows change, update this table to match. For Dockerfiles, proxy configuration, deployment scripts, or shared infrastructure, also validate the affected image/configuration with the checks used by its workflow.

- `mvn test` does **not** replace `mvn verify`: Failsafe integration tests named `*IT` must run. Check both Surefire and Failsafe reports, failures, errors, and skipped tests.
- A targeted Vitest run does **not** replace the full frontend suite. A passing test suite does **not** replace a production build.
- Wait for commands to finish and inspect exit codes and reports. Earlier results do not validate later changes; rerun checks affected by the final edits.
- Match CI's runtime and configuration. Document necessary local compatibility options. A different bundler, skipped phase, or mock infrastructure is not proof the CI command passes.

## Keep failures visible and tests deterministic

- Investigate the first meaningful failure and fix its cause. Do not stop after rerunning until a flaky test happens to pass.
- Never disable tests, weaken assertions, remove security coverage, add blanket retries, use `continue-on-error`, or skip build phases merely to make the pipeline green.
- Integration tests must pass together, not only individually. Account for cached Spring contexts, shared Kafka consumer groups, database fixtures, Redis keys, timers, sockets, and asynchronous work.
- Seed fixtures directly when worker provisioning is not the behavior under test. For real asynchronous flows, wait for a bounded, observable condition rather than arbitrary sleeps. Do not require every listener in one context to own a partition when other contexts share its consumer groups.
- Clean up test-owned resources. Restore only artifacts known to have been generated by the test run; preserve unrelated user changes.
- Keep applied versioned Flyway migrations immutable. Add a new migration and follow the workflow's migration guard.

## Finish the task with evidence

- Complete the requested behavior across all affected layers. Continue through failures and necessary fixes; do not hand back a partial implementation as finished.
- Inspect `git diff` and run `git diff --check`. Verify the diff contains only intended changes and no secrets or generated artifacts.
- Report the exact checks run, their results, and any checks that were skipped or blocked. If verification is blocked, attempt available remedies and state the concrete blocker; label the work as awaiting verification, not complete.
- When pushing or updating a PR is authorized, inspect CI for the latest pushed commit and resolve failures before calling it ready to merge. An earlier green run does not validate a newer commit. Never merge or deploy with required checks failing, pending, cancelled, or unverified.
- If changes remain local, say so. Claim “CI passed” only after verifying the remote run for the relevant commit. Local success reduces risk; it cannot guarantee remote infrastructure will never fail.
